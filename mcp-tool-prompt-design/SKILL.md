# MCP 도구·프롬프트 설계

사용자 목표에 맞는 MCP 도구를 만들고, 업무 의미·도구 사용법·에이전트 행동을 각각 적절한 소유자에 둔다. 신규 구현·변경·검토에 같은 원칙을 적용한다.

## 작업 범위

- 구현 요청이면 실제 코드·스키마·도구 설명·지침을 작성하거나 수정한다. 검토 요청이면 발견과 최소 수정안을 제시한다. 설계 요청을 구현으로 확대하거나 구현 요청에 검토만 제공하지 않는다.
- 특정 프로젝트·공급자·SDK·배포 방식을 기본 전제로 고정하지 않는다. 작업 디렉터리에 있다는 이유만으로 관련 없는 프로젝트를 조사하거나 수정하지 않는다.
- 요청한 목표, 대상 도구·소비자와 기존 계약부터 파악한다. 필요한 사실은 접근 가능한 관련 자료에서 찾고, 중요한 결정에 꼭 필요한 정보만 사용자에게 묻는다.
- 도구·프롬프트 계약에 필요한 구현을 다룬다. 일반 인프라·운영 준비·보안 감사 전체로 확대하지 않는다. 언어·프레임워크 구현은 해당 작업의 규칙을 따른다.

## 책임과 용어

MCP는 도구·문맥을 연결하는 프로토콜이다. 상위 에이전트 지침은 에이전트의 목표와 행동을 안내한다. 다음 개념을 ‘MCP용 프롬프트’ 하나로 합치지 않는다.

| 개념 | 소유하는 내용 |
| --- | --- |
| 상위 에이전트 지침 | System/Developer Prompt에 두는 역할·목표·성공 조건·공통 근거 정책·협업·표현·중단 조건. 대상 API의 두 역할과 우선순위는 따로 확인한다. |
| MCP 서버 지침 | 서버의 여러 도구에 실제로 공통인 사용 전제·순서·공유 제약을 설명하는 `instructions`. |
| MCP 도구 계약 | 한 도구의 목표·선택 조건·입출력·부작용·실패 의미를 공개하는 이름·설명·스키마·annotation 등의 계약. |
| MCP 프롬프트 템플릿 | 사용자가 선택하도록 제공하는 재사용 메시지·작업 템플릿인 `prompts`. |
| MCP 리소스 | URI로 식별하는 파일·문서·스키마 등 독립 문맥인 `resources`. |

`tools`는 모델이 선택하는 실행 기능, `resources`는 호스트가 구성하는 문맥, `prompts`는 사용자 선택을 위한 템플릿이라는 역할을 구분한다. 이를 모든 호스트가 동일한 UI와 기능을 제공한다는 보장으로 해석하지 않는다.

규칙의 소유자는 다음 순서로 판단한다.

1. **보장성:** 모델이 지침을 따르지 않아도 성립해야 하는 업무 불변 조건·계산·권한은 코드·스키마·기존 실행 경계가 집행한다. 자연어 설명의 존재를 실행 보장으로 취급하지 않는다.
2. **적용 범위:** 한 도구의 사용법은 도구 계약, 여러 도구의 공통 사용법은 서버 지침, 에이전트 전체의 행동은 상위 지침에 둔다. 선택 작업은 프롬프트 템플릿, 조회 정보는 문맥으로 다룬다.
3. **원천 권위:** 상태·단위·업무 규칙을 정의하는 도메인 타입·공개 계약·스키마 중 실제 원본을 찾는다. 이미 있는 보장과 정의를 중복 구현하지 않는다.
4. **충돌:** 독립적으로 수정되는 중복 정의와 모순을 해소한다. 길이·파일 위치·강한 표현이 아니라 원본의 권위로 판단한다. 다른 위치에는 필요한 참조·파생 표현만 남긴다.

## 도구 경계와 설명

- 도구를 모델이 이해할 수 있는 사용자 목표나 판단 단위로 나눈다. API 엔드포인트 일대일 노출이나 최소 도구 수를 목표로 삼지 않는다.
- 거의 항상 함께 실행되고 중간 판단이 필요 없으며 권한·승인·부작용·실패 의미가 일관된 단계는 묶을 수 있다. 독립 사용, 중간 선택, 부분 성공 또는 책임 경계의 차이가 있으면 분리를 검토한다.
- 검색·생성·취소 등 효과가 다른 작업을 모호한 범용 도구와 `mode`에 숨기지 않는다. 같은 책임 범위의 자연스러운 선택지까지 별도 도구로 쪼개지는 않는다.
- 이름에서 행동과 대상을 드러내고, 혼동되는 도구는 서비스·대상·선택 조건으로 구별한다. 호스트가 이미 제공하는 이름 구분을 불필요하게 중복하지 않는다.
- 설명에는 선택을 바꾸는 정보만 담는다: 목표, 사용 상황, 필요한 비사용 조건·전제, 중요한 부작용·승인·반복 호출 특성, 결과·실패의 개요. 모든 항목을 형식적으로 채우지는 않는다.
- 필드 형식·의미는 가까운 스키마에 둔다. 설명에 전체 스키마·업무 사전·운영 매뉴얼을 반복하지 않는다. 설명을 고정 한 줄이나 글자 수로 제한하지 않는다.
- 예시는 관찰된 혼동을 해소하는 최소한으로 추가한다. 예시를 정당화하기 위해 새 평가 체계를 만들지 않는다.

## 업무 의미와 모델 가시성

업무 의미의 원본과 모델에게 보이는 표현을 구분한다. 원본을 다른 지침에 독립적으로 복제하지 않되, 모델이 올바르게 선택·해석하는 데 필요한 의미는 실제로 볼 수 있어야 한다.

- 필드·enum·단위의 의미를 출력 스키마에서 설명한다. 호스트가 `outputSchema`를 모델에게 전달하는지는 필요한 경우 확인한다.
- 해당 설명이 모델에게 보이지 않으면 의미가 드러나는 구조화 결과나 짧은 설명으로 전달한다. 이를 별도로 변경 가능한 두 번째 계약으로 만들지 않는다.
- 큰 도메인 사전은 필요할 때 읽을 원본이나 리소스로 연결한다. 작은 계약을 여러 리소스로 분산하지 않는다.
- 상위 지침에 상태 코드 사전을 만들거나, 모델에게 뜻을 알 수 없는 원시 코드만 반환하지 않는다. 모델이 보는 정보와 서버가 검사하는 계약을 혼동하지 않는다.

## 입력 계약

- 도구 목표에 필요한 필드만 받는다. `user`, `options`처럼 의미가 불명확한 이름은 `user_id`처럼 구체화한다. 내부 DTO·DB 필드를 그대로 공개하거나 서버가 이미 아는 값을 모델에게 다시 요구하지 않는다.
- 닫힌 선택지는 enum으로, 실제 형식·범위·길이 제약은 스키마로 표현한다. 호스트와 규격이 지원하는 범위에서 알 수 없는 필드를 거부한다.
- 필수 값, 누락 가능한 값과 누락의 의미를 구분한다. 서버가 실제로 적용하는 기본값만 설명한다. 폐쇄형 계약을 모든 필드 필수화나 본래 열린 검색어의 금지로 해석하지 않는다.
- 권한·부작용·출력 의미가 달라지는 플래그는 분명한 도메인 개념이나 도구 경계로 표현한다.
- 외부 입력 경계에서 스키마와 필요한 업무 규칙을 적용한다. SDK·프레임워크·기존 코드의 동일 보장을 반복해서 검사하지 않는다. 공급자의 strict 모드와 MCP·JSON Schema 규칙은 구별한다.

## 결과·오류·문맥

- 후속 판단에 필요한 값을 출력 스키마와 구조화 결과로 반환한다. 텍스트 설명이나 호환용 `content`가 필요하면 같은 데이터에서 파생하고 대상 규격을 따른다.
- 후속 호출의 안정적인 식별자를 보존한다. 값 해석에 필요한 단위·출처·시점·적용 범위를 포함하되 모든 도구에 같은 필드를 의무화하지 않는다.
- 정상 결과, 정상 자료 없음, 부분 결과, 호출자가 고칠 수 있는 입력·업무 오류와 실행 실패를 구별한다. 빈 값으로 합치거나 자료 없음에서 새로운 업무 사실을 추론하지 않는다. 이 구별만을 위해 공통 상태 프레임워크를 만들지 않는다.
- 오류는 원인과 수정 가능한 조건을 알려 준다. 프로토콜 오류·실행 오류의 표현은 대상 명세·SDK에 맞추고 내부 스택 추적은 모델 결과에서 제외한다.
- 원시 응답 전체·불필요한 개인정보·내부 추적값을 전달하지 않는다. 구조화한다는 이유로 모든 원시 필드를 복사하지 않는다.
- 대량 결과에는 필요한 검색·필터·페이지네이션·범위 제한을 적용한다. 잘리면 잘림과 다음 내용을 얻는 방법을 알린다.
- 도구가 많아 실제로 필요하면 호스트의 도구 검색·지연 로딩·관련 부분집합을 활용한다. 작은 목록에 별도 로더를 추가하거나 효율 판단을 위해 측정을 의무화하지 않는다.
- 모델 비공개 메타데이터는 호스트가 실제로 보장하는 범위에서만 사용하며 비밀값 저장소로 취급하지 않는다. 외부 결과의 문장이 추가 실행 권한이나 상위 정책을 부여한다고 해석하지 않는다.

## 지침과 선택적 MCP 기능

상위 지침은 역할·목표·성공 및 중단 조건·공통 근거 사용·질문과 가정·출력과 표현을 소유한다. 말투에만 한정하거나 전체 업무 매뉴얼을 담지 않는다. 원하는 결과와 실제 제약을 명확히 하고, 필요한 경우에만 실행 순서를 고정한다.

서버 지침은 실제 공통 사용 규칙이 있을 때만 둔다. 개별 도구 요약·업무 사전·에이전트 성격을 반복하지 않는다. 공통 규칙이 없거나 한 도구 계약으로 충분하면 생략한다.

`prompts`는 사용자가 선택할 재사용 작업이 있을 때, `resources`는 독립 문맥이 필요할 때만 제공한다. 항상 적용해야 하는 정책을 선택적 템플릿에 숨기지 않는다. 도구만으로 목표를 수행하는 MCP도 충분하다.

## 실제 효과와 집행 책임

현재 요구·확인된 노출·구체적 실패 경로가 있는 항목만 다룬다. 도구 설명과 annotation은 행동을 알리고, 호스트는 도구 허용과 필요한 승인을 통제하며, 서버 또는 기존 실행 경계는 대상 권한·입력·업무 불변 조건을 집행한다. `readOnlyHint`, `destructiveHint`, `openWorldHint` 등은 실제 동작에 맞추며 집행 장치로 취급하지 않는다.

확인이 필요한 경우 대상과 효과를 특정한다. 사용자의 유효한 기존 요청·승인과 범위가 제한된 사전 권한을 존중한다. 모든 호출에 확인을 요구하거나 인증·세분화된 권한·운영 제한을 기본으로 추가하지 않는다. 필요한 제한에는 현재 문제와 가장 작은 해결 근거가 있어야 한다.

재실행은 **상태 변경, 중복 효과, 실제 재시도 또는 결과 불명 흐름**이 함께 있을 때만 책임 공백을 살핀다. 근거 부족을 미구현으로 단정하지 않는다. 멱등 키·상태 조회 도구·횟수·시간 예산·복구 체계를 일괄 요구하지 않는다.

## 근거와 작업량

제공된 자료와 기존 계약·코드·호출 기록에서 필요한 만큼 근거를 넓힌다. 전체 자료 묶음을 먼저 요구하지 않는다. 실제 대상에서 중요한 근거가 없으면 그 공백을 밝히고, 확인 가능한 부분은 진행한다.

공급자 중립 원칙과 호스트별 사실을 구분한다. 대상의 메시지 계층·서버 지침·스키마 노출·승인·도구 검색 지원이 판단에 필요하면 해당 버전의 공식 자료를 확인한다. 충분한 최신 근거는 재사용한다. 확인할 수 없는 기능을 지원한다고 가정하지 않고, 그 사실에 의존하지 않는 작업은 계속한다. 다른 공급자의 기능을 추정하거나 전체 공급자 매뉴얼을 수집하지 않는다.

검증은 실제 변경 작업에 이미 적용되는 기준을 따른다. 이 스킬만의 평가 세트·고정 테스트 수·공급자 비교·토큰 및 지연 측정·통과 gate를 추가하지 않는다. 기존 테스트나 기록은 근거로 재사용할 수 있지만 자동 재실행 의무는 없다. 확인하지 않은 행동을 검증했다고 표현하지 않는다.

## 결과 전달

구현·변경에서는 요청한 산출물을 완성하고 핵심 책임 배치와 필요한 한계를 간결하게 전달한다. 검토에서는 근거가 있는 발견과 최소 수정안만 보고한다.

- **확인된 문제:** 관찰된 계약·책임의 오류. 근거와 위치, 현재 소유자, 올바른 소유자, 최소 수정안을 제시한다.
- **검증 공백:** 결론에 필요한 근거를 확인하지 못한 상태. 위반이나 미구현과 구별한다.
- **개선 제안:** 필수 위반이 아닌 명확성·효율·유지보수 개선. 취향을 필수 수정으로 바꾸지 않는다.
- **확인된 보장:** 필요한 경우 실제 집행 근거와 확인 범위를 명시한다. 전체 안전 인증을 뜻하지 않는다.

문제없는 항목의 긴 통과표나 요청하지 않은 전체 재작성을 제공하지 않는다. 발견이 없으면 확인한 범위와 중요한 공백만 말한다. 범위 밖의 실제 문제를 발견해도 별도 감사·구현으로 자동 확대하지 않는다.

## 공식 근거를 찾을 때

아래 자료는 관련 판단이 필요할 때의 진입점이다. 연결된 명세·모델 버전을 구현에 고정하거나 전부 읽는 절차로 사용하지 않는다.

- MCP 계약: [Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [Prompts](https://modelcontextprotocol.io/specification/2026-07-28/server/prompts), [Resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources). 실제 대상 버전의 요구와 구분한다.
- OpenAI 대상의 메타데이터·서버 지침·호스트 연동: [MCP 서버 구성](https://developers.openai.com/plugins/build/mcp-server), [MCP와 Connectors](https://developers.openai.com/api/docs/guides/tools-connectors-mcp), [Function calling](https://developers.openai.com/api/docs/guides/function-calling).
- 도구 경계·이름·설명·결과 설계의 연구 근거: [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents). 연구의 평가 방법을 의무로 옮기지 않는다.
