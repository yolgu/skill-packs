# 브랜치 재구성

옛 작업 브랜치가 담은 **변경**만 골라 새 기준 위에 새 브랜치로 다시 만든다. 옛 브랜치는 건드리지 않는다. 중간에 틀려도 옛 브랜치와 보관 태그가 그대로 있어서 처음부터 다시 할 수 있다.

## rebase 대신 이 방법을 쓰는 이유

- **rebase는 커밋을 하나씩 다시 적용한다.** 중간 커밋마다 충돌이 나고, 옛 기준에서 끌어온 병합 커밋과 되돌림 커밋까지 다시 만들어진다.
- **최종 상태를 한 번에 적용하면 충돌은 한 번만 푼다.** 그리고 결과를 옛 변경과 파일 단위로 대조할 수 있다.
- **커밋 단위 기록이 중요할 때는 예외다.** 커밋 수가 적고 각 커밋이 깨끗하면 새 브랜치에서 `git cherry-pick -x <옛 기준>..<옛 끝>`을 써도 된다. 대조(5단계)는 똑같이 한다.

## 먼저 정할 것

아래는 사용자의 결정이다. 저장소 규칙이나 기본값으로 정해지지 않는 것만 하나씩 묻고, 물을 때 추천안을 함께 낸다.

1. **새 기준**: 저장소 규칙 스킬이 있으면 그 규칙에 따라 작업 종류에 맞는 기준 브랜치를 정한다.
2. **새 브랜치 이름**: 저장소의 이름 규칙을 따른다(예: `<종류>/<영역>/<주제>`). 옛 이름을 다시 쓰지 않는 것을 권한다. 옛 원격 브랜치와 섞이지 않고, 둘을 나란히 비교할 수 있다.
3. **기록 방식**: 최종 상태를 담은 새 커밋(권장)인지, 커밋별 재적용인지 정한다.
4. **뺄 것**: 시안, 실험 파일, 다른 기능의 변경.
5. **다른 브랜치와 공유할 커밋**: 예를 들어 두 기능이 같은 로컬 실행 설정을 쓰면 그 커밋을 함께 쓴다. 같은 커밋을 공유해야 나중에 두 기능을 병합할 때 충돌하지 않는다.
6. **원격 반영 범위**: 새 브랜치와 보관 태그를 올릴지 정한다. 옛 원격 브랜치는 나중에 지운다.

## 절차

### 1. 사전 확인

- 작업 트리가 깨끗한지, 다른 세션이나 빌드가 같은 폴더를 쓰는지 본다.
- `git fetch origin --prune --tags`
- 셸이 zsh면 패턴은 따옴표로 감싸고, 여러 값은 배열로 다룬다. 프로젝트나 상위 작업 공간에 로컬 실행 환경 문서가 있으면 해당 문서의 셸 명령 규칙을 따른다.

### 2. 보관과 범위 확정

옛 끝에 주석 태그를 붙인다. 이후 모든 비교는 이 태그를 기준으로 한다. 옛 브랜치에 원격에 없는 커밋이 있으면, 이 태그를 원격에 올려 보존한다(승인 필요). 태그 이름의 날짜는 옛 끝 커밋의 커밋 날짜로 한다. 저장소 규칙에 다른 정의가 있으면 그것을 따른다.

```bash
git log -1 --format=%cd --date=format:%Y%m%d <옛 끝>
git tag -a archive/<이름>-<YYYYMMDD> <옛 끝> -m "<보관 이유>"
old_base=$(git merge-base <옛 끝> <옛 브랜치를 딴 브랜치 또는 그 보관 태그>)
git log --oneline --no-merges "$old_base"..<옛 끝>
```

- **옛 기준은 반드시 "옛 브랜치가 갈라져 나온 곳"이다.** 새 기준으로 잡으면 두 기준 사이의 차이 전체가 변경으로 딸려 온다.
- **목록에 다른 작업의 커밋이 섞여 있으면** 사용자에게 보여 주고 뺄지 정한다.

### 3. 미리 계산 (브랜치를 움직이지 않는다)

```bash
git merge-tree --write-tree --name-only --merge-base "$old_base" <새 기준> <옛 끝>
```

- 종료 코드 1이면 충돌이다. 첫 줄 뒤에 충돌 파일 목록이 나온다.
- `git replay`는 기본 동작이 브랜치를 실제로 옮긴다. 쓰지 않거나 `--ref-action=print`를 붙인다.
- 시험 삼아 rebase나 cherry-pick을 해 볼 때는 버릴 임시 브랜치에서 한다.

### 4. 새 브랜치에 적용

```bash
git switch --no-track -c <새 브랜치> <새 기준>
squash=$(git commit-tree "<옛 끝>^{tree}" -p "$old_base" -m "rebuild source")
git cherry-pick --no-commit "$squash"
```

**왜 이렇게 하나**: 이 묶음 커밋은 부모가 옛 기준이고 내용은 옛 끝이다. 그래서 cherry-pick이 옛 기준, 새 기준, 옛 끝으로 3방향 병합을 한다. 그 결과 옛 변경만 새 기준 위에 얹힌다.

- **충돌**: 양쪽 의도를 확인해 푼다. 한쪽을 통째로 택하는 해결은 무엇이 빠지는지 알리고 승인을 받은 뒤에만 쓴다.
- **뺄 것**:
  - 새 기준에 원래 있던 파일은 `git restore --source=<새 기준> --staged --worktree -- <경로>`로 되돌린다.
  - 새로 생긴 파일은 `git rm -f -- <경로>`로 지운다.
- **공유 커밋을 먼저 둘 때**: 공유할 경로만 stage해서 먼저 커밋한다. 이미 다른 브랜치에 있는 커밋이면 그 커밋 위에서 시작한다.
- **커밋 메시지**: 저장소 규칙을 따른다. 본문에 옛 범위(`<옛 기준>..<옛 끝>`)와 뺀 것을 적는다.

### 5. 변경 대조

```bash
python3 <이 스킬 폴더>/scripts/compare_delta.py -C <저장소> \
  --old-base "$old_base" --old-tip archive/<이름>-<YYYYMMDD> \
  --new-base <새 브랜치의 대조 시작점> --new-tip <새 브랜치> \
  --expect <일부러 바꾼 경로> --expect <뺀 폴더>/
```

- 스크립트는 파일마다, 더한 줄 묶음과 뺀 줄 묶음이 옛 변경과 같은지 본다. 의도하지 않은 차이가 있으면 종료 코드 1이다.
- `--expect`에는 일부러 다르게 만든 경로만 넣는다. 뺀 시안, 충돌을 푼 파일, 옮긴 파일이 여기에 해당한다. `/`로 끝나면 폴더 전체다.
- 처음에는 `--expect` 없이 돌린다. 나온 차이를 하나씩 설명할 수 있는지 본 다음에 넣는다.
- 설명할 수 있는 차이는 셋뿐이다.
  - 뺀 것
  - 충돌을 푼 것
  - 새 기준이 같은 줄을 먼저 고쳐서 생긴 차이
  - 이 셋이 아니면 적용이 잘못된 것이다.
- 공유 커밋을 따로 뒀으면 대조 시작점을 그 커밋 위로 잡는다. 또는 공유 커밋의 파일을 `--expect`에 넣는다.

### 6. 검증

- 저장소의 테스트와 정적 검사를 실행한다. 실행 전에 `toolchain-preflight` 스킬로 런타임 버전을 맞춘다.
- 실패하면 새 기준에서도 같은 테스트가 실패하는지 먼저 본다.
  - 기준에서도 실패하면 이번 재구성과 무관하다. 보고에 따로 적는다.
  - 공유 커밋 때문에 생긴 실패면, 기능 커밋에 섞지 말고 별도 커밋으로 고친다.

### 7. 앞으로의 병합 미리 보기

새 브랜치가 나중에 만날 브랜치를 미리 계산해 충돌을 기록한다. 개발 통합 브랜치나 함께 출시할 기능 브랜치가 그 대상이다.

```bash
git merge-tree --write-tree --name-only <통합 브랜치> <새 브랜치>
```

### 8. 원격 반영 (할 때마다 승인)

```bash
git push --atomic origin <새 브랜치>:refs/heads/<새 브랜치> refs/tags/archive/<이름>-<YYYYMMDD>
git ls-remote origin 'refs/heads/<새 브랜치>' 'refs/tags/archive/<이름>-<YYYYMMDD>'
git branch -u origin/<새 브랜치> <새 브랜치>
```

- 브랜치와 태그를 한 번에 올리고, 원격이 로컬과 같은 커밋을 가리키는지 확인한다.
- 옛 원격 브랜치 삭제는 별도로 승인을 받는다. 저장소 규칙 스킬의 정리 절차를 따른다.

### 9. 기록

작업 공간의 계획 문서 폴더(예: `docs/plans/<날짜>-<주제>-result.md`)에 남긴다.

- 저장소마다 새 기준, 새 브랜치 끝, 보관 태그를 담은 표
- 커밋마다 담은 것과 뺀 것
- 대조 결과(`--expect`로 넘긴 경로와 그 이유), 테스트 결과
- 7단계에서 예상한 충돌과 푸는 방향
- 진행 중 생긴 사고와 후속 일

## 여러 저장소를 함께 옮길 때

같은 기능이 앱과 서버에 걸쳐 있으면 새 브랜치 이름을 통일하고, 저장소마다 같은 절차를 밟는다. 결과는 표 하나로 모은다. 저장소마다 기준이 다를 수 있다(예: 서버는 master, 앱은 develop). 그러니 새 기준은 저장소마다 저장소 규칙으로 정한다.

## 하지 않는 것

- 옛 브랜치를 그 자리에서 rebase하거나 reset하지 않는다.
- 공유 브랜치(master, develop, review)를 강제로 덮어쓰지 않는다.
- 대조(5단계) 없이 완료를 보고하지 않는다.
