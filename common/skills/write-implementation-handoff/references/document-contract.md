# 구현 인계 문서 계약

이 참고 자료는 완료된 한 구현 단위를 `README.md`, `blocker.md`, `next.md` 세 파일로 설명할 때 적용한다. 문서를 장기 운영 체계나 프로젝트 전체 백과사전으로 확장하지 않는다.

## 공통 기준

독자는 이번 구현에 참여하지 않은 개발자나 운영 담당자다. 이전 대화나 작성자의 기억 없이 세 파일을 한 번 읽고 다음을 이해할 수 있어야 한다.

- 무엇을 왜 구현했는가
- 구현 전후에 무엇이 달라졌는가
- 최종 구조에서 누가 무엇을 실행하며 데이터와 요청이 어디로 이동하는가
- 어떤 선택을 유지하거나 버렸고 그 이유는 무엇인가
- 실제로 어디까지 검증했으며 무엇은 검증하지 않았는가
- 구현 중 어떤 판단이 바뀌었는가
- 이번 범위에서 하지 않은 일은 무엇이며 왜 남았는가

자연스러운 문장을 우선하고, 정확한 순서나 작은 구조가 실제로 더 잘 보일 때만 목록·표·텍스트 그림을 사용한다. 같은 필드를 모든 항목에 강제하거나 링크를 따라가야만 이해되는 문서로 만들지 않는다. 실제 파일을 확인해야 하는 핵심 위치만 문장 속에서 연결한다.

정확한 식별자는 바꾸지 않는다. 설명에서는 불필요한 기술 번역투를 피하고, 행동의 주체와 시작 조건을 드러낸다. “자동으로 처리된다”로 끝내지 말고 어떤 명령이나 사건이 어떤 프로세스를 시작하며 사용자가 별도로 해야 하는 일이 무엇인지 쓴다.

## README.md

README는 이번 구현의 주 설명서이며 다른 두 파일을 먼저 읽게 해서는 안 된다. 다음 흐름을 구현에 맞게 자연스럽게 연결한다.

1. 구현의 목적과 이전 상태
2. 이번 완료 단위와 의도적으로 제외한 범위
3. 최종 구조, 구성요소 경계와 데이터·요청 흐름
4. 중요한 설계 선택과 버린 대안의 이유
5. 설정·코드·스크립트·실행 프로세스의 책임
6. 사람이 실제로 입력하는 명령과 핵심 내부 실행 흐름
7. 사람이 나중에 고칠 때 함께 생각해야 할 연결
8. 실제 검증 결과와 확인하지 않은 범위

공개 명령이 wrapper를 거치면 이해에 필요한 단계까지만 푼다. 예를 들어 다음 정도의 관계를 설명할 수 있다.

```text
사용자가 입력하는 공개 명령
→ 저장소의 실행 진입점
→ 핵심 build·배포·검증 명령
→ 생성되는 산출물 또는 실행 상태
```

내부 셸 명령을 전부 복사하지 않는다. 독자가 실제로 입력할 명령, 자동으로 이어지는 범위, 실패하면 멈추는 경계와 별도로 해야 할 일을 이해할 수 있으면 충분하다.

구조나 설정을 직접 관리할 때의 주의점은 변경 대응표로 만들지 않는다. 예를 들어 metadata 하나가 배포 설정과 검증 계약에 함께 영향을 준다면, 왜 한쪽만 고치면 서로 어긋나는지를 문장으로 설명한다.

검증 결과는 `구현 존재`, `로컬 검증`, `배포`, `운영 전환`을 필요에 따라 구분한다. 날짜, commit, 실행 ID는 근거를 찾는 데 필요할 때만 검증 문단에서 제한적으로 사용한다. 원문 로그와 긴 ID 목록을 붙이지 않는다.

## blocker.md

blocker는 오류 목록이나 현재 열려 있는 문제만을 뜻하지 않는다. 다음 사람이 같은 증상을 잘못 해석하지 않도록 구현 중 중요한 판단의 변화를 보존한다.

문제별 서사는 다음 내용을 자연스럽게 잇는다.

```text
관찰한 증상
→ 처음 의심한 원인
→ 추가로 확인한 증거
→ 바뀐 판단과 확인된 원인 또는 경계
→ 적용한 해결과 남은 불확실성
→ 같은 증상에서 먼저 볼 지점
```

초기 가설이 틀렸다면 최종 결론만 남기지 말고 무엇이 판단을 바꿨는지 쓴다. 실제 실행을 막은 장애와 코드 검토로 미리 발견한 위험도 구분한다. 예방한 위험을 이미 발생한 사고처럼 쓰지 않는다.

사소한 오타, 단순 출력 잘림, 코드만 보면 충분한 작은 수정과 원문 로그 대량 복사는 제외한다. `상태`, `영향`, `담당자`, `원인` 같은 고정 필드를 사건마다 반복하지 않는다. 의미 있는 blocker가 없다면 한두 문단으로 그 사실만 명시한다.

## next.md

next는 다음 구현 계획이 아니라 이번 구현 뒤에 남은 맥락이다. 다음 성격의 항목이 실제로 있을 때만 설명한다.

- 계정·접근 권한·업무 결정처럼 다른 사람이 먼저 해야 하는 일
- 이번 완료 단위보다 범위가 커서 미룬 기능
- 현재 기능에는 필요하지 않지만 반복 비용을 줄일 수 있는 선택적 개선

각 항목은 현재 알려진 사실, 이번 범위에서 하지 않은 이유, 부족한 자료나 결정, 다시 판단할 수 있는 조건을 문장으로 잇는다. 실제 행동 주체가 이해에 필요하면 누가 무엇을 해야 하는지 분명히 쓴다.

아직 조사하지 않은 작업의 구현 순서, 파일 변경 목록, 명령, 고정 완료 기준과 복구 절차를 만들어 내지 않는다. 우선순위·담당자·상태·일정 표도 강제하지 않는다. 남은 일이 없다면 새로운 일을 억지로 만들지 말고 그 사실만 짧게 설명한다.

## 내용과 보안 경계

세 파일에는 실제 비밀번호, Token, Private Key, 서비스 계정 JSON, Provider Key, Secret 본문과 kubeconfig 내용을 넣지 않는다. 과거 자료에서 민감한 값의 존재가 중요하면 값을 재현하지 않고 노출 가능성과 필요한 대응 주체만 설명한다.

사람용 문서와 같은 내용을 AI용 field 문서로 복제하지 않는다. 상태·담당자·영향도·재발 조건을 모두 고정 field로 만들지 않는다. 세 파일은 이번 구현의 지식 격차를 한 번 줄이는 결과물이지 계속 갱신하는 운영 기록이 아니다.

## 수동 확인

작성 뒤 세 파일을 순서대로 읽고 다음을 직접 확인한다.

- README가 다른 파일 없이도 구현의 전체 흐름을 설명하는가
- blocker가 증상과 판단 변화를 시간순 기록의 단순 복사 없이 전달하는가
- next가 구현 계획으로 변하지 않았는가
- 같은 사실이 세 파일에서 충돌하지 않는가
- 언급한 경로·명령·링크가 실제로 존재하는가
- 비밀값과 원문 실행 결과가 복사되지 않았는가
- 정확히 세 파일만 새로 생겼는가

새 검사 프로그램을 만들지 않는다. 기존 근거와 값싼 정적 확인을 사용하고, 문서화를 이유로 구현을 다시 실행하지 않는다.
