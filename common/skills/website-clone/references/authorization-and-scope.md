# Authorization and scope

## Allowed purposes

Use this workflow for an authorized migration, rebuild, interoperability effort, recovery, testing fixture, owned-property redesign baseline, or learning exercise. A public URL is inspectable but does not by itself grant rights to redistribute protected code, assets, marks, copy, or data.

## Refuse or stop

Do not help create phishing pages, deceptive impersonation, credential capture, bypasses for login or bot controls, fake support or payment surfaces, or a clone intended to mislead users about its operator. Do not collect cookies, tokens, private responses, account data, or hidden secrets.

If the user controls the target or gives a clear authorized purpose, proceed within that scope. If a third-party target is ambiguous, state the narrow assumption: reproduce visible presentation and client behavior for review, without protected backend behavior or deceptive branding.

## Scope record

Before editing, name:

- target URL or supplied images;
- authorized purpose;
- pages, sections, states, and locales;
- desktop, tablet, and mobile sizes;
- interactions and motion;
- assets permitted for local use;
- whether copy is exact, replaced, or supplied by the user;
- backend, authentication, payment, analytics, SEO, accessibility, and data boundaries;
- existing repository stack and paths that may change;
- completion threshold and accepted deviations.

Multiple hosts remain separate targets with separate captures, assets, notes, and output paths.

## Dependency and asset approval

Prefer the repository's existing dependencies and asset pipeline. Ask before adding a package, downloading a restricted asset, using a trademark beyond the authorized context, or committing large binary files. Record the source and local destination of retained assets.
