# PRD 작성

사용자가 만들려는 소프트웨어 기능이나 앱의 PRD를 Markdown 파일 하나로 작성한다. 해결할 문제와 대상 사용자, 목표, 범위, 필요한 동작, 수용 조건, 성공 기준을 설명한다. 기술 계획이나 구현 작업으로 이어가지 않는다.

## 입력과 맥락

1. 사용자의 설명에서 대상 사용자, 해결할 문제, 기대하는 결과, 주요 동작, 명시적 제약을 파악한다. 기존 PRD의 수정 요청이면 해당 문서를 읽고 요청 범위에 맞게 갱신한다. 새 기능이면 새 PRD를 만든다.
2. 기존 프로젝트에서는 관련 문서와 현재 기능을 확인해 용어, 동작, 제약을 반영한다. 새 프로젝트처럼 참고 자료가 없으면 사용자 설명으로 진행한다. 이번 기능과 무관한 저장소 전체를 조사하지 않는다.
3. 시장 조사나 경쟁 제품 조사는 수행하거나 PRD에 추가하지 않는다. 문제, 대상 사용자, 기대 가치에 관해 확인되지 않은 주장을 사실처럼 쓰지 않는다.
4. 기능 범위나 사용자 경험이 크게 달라지고 합리적인 기본값도 없는 선택만 사용자에게 질문한다. 답을 반영한 후 PRD를 작성한다. 나머지 빈 부분은 합리적으로 결정하고 필요한 가정만 문서에 밝힌다. 앱 전체 입력이 한 문서에 담기 어려울 만큼 넓으면 임의로 여러 문서로 나누기 전에 초점을 질문한다.

## 문서 작성

프로젝트에 PRD 양식이 있으면 그 형식을 따르되 아래 내용은 빠뜨리지 않는다. 관례가 없으면 다음 흐름을 사용한다.

1. **문제와 배경:** 해결할 문제와 확인된 현재 상황.
2. **대상 사용자와 목표:** 영향을 받는 사용자와 달성하려는 사용자 및 제품 결과.
3. **범위:** 이번 PRD에 포함되는 동작과 제외되는 동작.
4. **사용자 시나리오와 수용 조건:** 중요한 사용자 흐름을 우선순위에 따라 서술하고, 각 흐름의 완료 여부를 관찰할 수 있는 조건.
5. **기능 요구사항:** 제공해야 할 동작을 명확하고 검증 가능한 문장으로 기술.
6. **성공 기준:** 제품이나 사용자 결과를 확인할 수 있는 기준. 수치 목표는 사용자 설명이나 확인한 프로젝트 자료에 근거가 있을 때만 사용한다.

경계 사례, 핵심 개념이나 데이터 대상, 가정, 제약은 필요한 경우에만 추가한다. 형식을 채우려고 빈 섹션이나 근거 없는 요구사항을 만들지 않는다. 사용자가 명시한 기술 제약은 보존하되, 새로운 기술 스택, 아키텍처, API 설계를 선택하지 않는다. 무엇을 왜 만들어야 하는지 이해할 수 있는 표현을 사용한다.

작성 중에 목표, 범위, 시나리오, 요구사항, 수용 조건, 성공 기준이 서로 맞는지 확인하고 모호하거나 검증할 수 없는 문장은 바로 고친다. 별도 체크리스트 파일이나 승인 관문은 만들지 않는다.

## 저장과 완료

- 한 번의 호출에서 PRD 파일 하나만 작성하거나 갱신한다.
- 사용자가 경로를 지정했다면 그 경로를 사용한다. 그렇지 않으면 프로젝트의 PRD 저장 관례를 따르고, 관례가 없으면 `docs/prd/<기능명>.md`에 저장한다.
- 기존 PRD를 수정할 때는 요청과 무관한 내용을 보존한다. 새 기능은 새 파일로 작성한다.
- 프로젝트의 기존 기획 문서 언어가 분명하면 그 언어를 따른다. 관례가 없으면 사용자 요청 언어를 따른다.
- 완료 후 채팅에는 PRD 파일 링크와 핵심 내용만 짧게 알린다. 문서 전문을 채팅에 중복 출력하지 않는다.

이 스킬을 실행하기 위해 Spec Kit CLI, `.specify/` 상태, Git 브랜치, 확장 훅, 다른 스킬이나 프롬프트를 요구하지 않는다. 기술 계획, 작업 목록, 구현, 배포, 후속 명령 자동 실행도 수행하지 않는다.
