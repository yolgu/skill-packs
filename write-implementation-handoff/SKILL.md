# Write Implementation Handoff

## 목적과 시작 조건

사용자가 완료했다고 선언한 이번 구현을 사람이 한 번 읽고 따라잡을 수 있는 인계 문서로 작성한다. 구현 규모나 완료 여부를 다시 심사하지 말고, 구현을 계속하거나 다음 작업을 계획하지 않는다.

명시적으로 호출된 경우에만 실행한다. 인터뷰를 새로 시작하거나 요구사항·구현 계획 문서를 만들지 않는다. 환경에서 찾을 수 없는 한 가지 사실이 결과 경로 또는 설명 범위를 실질적으로 바꿀 때만 짧게 질문한다.

본문은 사용자가 다른 언어를 명시하지 않는 한 자연스러운 한국어로 작성한다. 코드, 명령, 경로와 외부 식별자는 실제 이름을 유지한다.

## 필수 참고 자료

문서를 작성하기 전에 [references/document-contract.md](references/document-contract.md)를 처음부터 끝까지 읽고 세 파일의 역할과 문체 경계를 적용한다. 참고 자료의 일반화된 예시를 대상 저장소의 사실로 복사하지 않는다.

## 실행 절차

### 1. 이번 구현의 범위를 복원한다

현재 대화, 저장소 지침, 현재 기준 문서, 관련 계획, Git 상태·diff·관련 commit, 실제 구현 파일, 테스트와 이미 남아 있는 빌드·실행 기록을 필요한 범위에서 읽는다. 공개 명령과 중요한 설정은 정의와 사용 위치를 함께 추적한다. 첫 검색 결과나 과거 계획만으로 현재 구현을 단정하지 않는다.

사용자에게 다시 설명을 요구하기 전에 환경에서 알 수 있는 사실을 직접 찾는다. 이미 확보된 근거를 재사용하며 문서화를 이유로 장시간 build, 배포, 클러스터·DB 재생성, 외부 서비스 호출이나 저장소·데이터 전체 Hash를 실행하지 않는다. 경로 존재, 현재 설정, 명령 연결과 짧은 정적 검사처럼 값싼 확인만 수행한다.

### 2. 출력 경계를 정한다

이번 구현 단위를 나타내는 짧은 영문 kebab-case 이름을 정하고 저장소 루트의 `runbooks/<implementation-scope>/`를 대상으로 삼는다. 프로젝트 전체 이름이나 사용 기술만으로 이름을 짓지 않는다. 이름 후보가 둘 이상이고 선택에 따라 구현 범위가 달라질 때만 사용자에게 한 번 확인한다.

대상 디렉터리나 세 대상 파일 중 하나라도 이미 있으면 아무것도 덮어쓰거나 수정하지 말고 중단한다. 날짜·숫자 접미사를 자동으로 붙이지 않는다. 기존 handoff의 수정은 이 Skill의 범위가 아니다.

### 3. 사실과 검증 범위를 분리한다

사용자의 완료 선언은 시작 조건으로 받아들이되, 코드 존재, 로컬 검증, 배포와 운영 전환을 서로 다른 사실로 다룬다. 확인 근거가 없는 테스트나 실행을 통과했다고 쓰지 않는다. 현재 구현과 과거 계획 또는 실행 기록이 충돌하면 확인된 범위와 불확실한 범위를 구분한다.

비밀번호, Token, Private Key, 서비스 계정 JSON, Provider Key, Secret과 kubeconfig 본문을 읽은 문서에 복사하지 않는다. 값이 노출될 수 있는 검색은 출력하지 말고, 필요한 경우 존재와 대응 경계만 설명한다.

### 4. 정확히 세 파일을 새로 작성한다

다음 파일만 만든다.

```text
runbooks/<implementation-scope>/
├── README.md
├── blocker.md
└── next.md
```

`README.md`에는 구현 목적, 이전 상태, 최종 구조와 동작, 중요한 선택과 제외한 대안, 파일·프로세스의 책임, 실제 사용 명령과 그 뒤의 핵심 실행 흐름, 사람이 직접 고칠 때 알아야 할 연결, 확인한 범위와 확인하지 않은 범위를 하나의 흐름으로 설명한다.

`blocker.md`에는 의미 있었던 문제만 증상, 초기 가설, 추가 증거, 바뀐 판단, 해결과 남은 불확실성의 이야기로 남긴다. 실제 장애와 검토 중 미리 막은 위험을 구분한다. 의미 있는 문제가 없으면 내용을 만들지 말고 그 사실만 짧게 쓴다.

`next.md`에는 이번에 하지 않은 일, 미룬 이유와 다시 판단하는 데 필요한 맥락만 쓴다. 다음 구현의 상세 계획, 파일 변경 목록, 명령과 작업 대장을 만들지 않는다. 남은 일이 없으면 그 사실만 짧게 쓴다.

추가 README, 문제별 문서, AI용 복제 문서, 상태표, 책임 대응표, 정기 검토 체계나 문서 생성용 script를 만들지 않는다. 기존 기준 문서, AI 문맥 캐시, 검사 프로그램과 구현 파일을 수정하지 않는다.

### 5. 사람이 읽는 기준으로 확인한다

세 파일을 처음부터 끝까지 직접 읽는다. README만으로 구현의 목적부터 검증 범위까지 이해할 수 있는지, blocker에서 초기 가설과 최종 판단이 뒤섞이지 않았는지, next가 실행 계획으로 변하지 않았는지 확인한다. 같은 사실을 세 파일에서 다르게 말하지 않는지 확인한다.

언급한 경로와 명령이 실제 구현과 맞는지 대조하고 필요한 내부 링크가 존재하는지 확인한다. 실제 자격 정보가 들어가지 않았는지 값을 노출하지 않는 방식으로 점검한다. 새 파일은 일반 `git diff --check`에서 빠질 수 있으므로 후행 공백과 기본 Markdown 문제를 파일 자체에서도 확인한다. 새 Python 문서 검사기를 만들거나 기존 검사기를 수정하지 않는다.

생성된 파일이 정확히 세 개인지, 다른 파일과 공유 상태가 바뀌지 않았는지 마지막으로 확인한다. 결과를 자동으로 stage, commit 또는 push하지 않는다.

## 완료 응답

세 파일의 절대 경로와 각각 무엇을 설명하는지 간결하게 알린다. 어떤 근거를 재사용했고 어떤 장시간 검증을 다시 실행하지 않았는지, 확인되지 않은 범위가 문서에 어떻게 구분됐는지를 필요한 만큼만 설명한다. 결과 문서 안에는 Skill 지침, 인터뷰 과정이나 AI가 작성했다는 제작 흔적을 남기지 않는다.
